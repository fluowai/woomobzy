# WooTech AI Workforce Builder - Implementation Plan

## Executive Summary

Complete rebuild of the AI Agents module from a **template-based card system** to an **AI-driven Workforce Builder** where the platform understands the business operation and automatically creates, configures, tests, and deploys a team of specialized AI agents.

---

## 1. Current State Analysis

### Existing Architecture (To Be Replaced)

| Component | Current Approach | Issues |
|-----------|------------------|--------|
| **Agent Creation** | 6 fixed templates (Zya, Otto, Nexus, Max, Íris, Eco) | Rigid, doesn't adapt to business model |
| **Configuration** | Manual wizard with 7 tabs | Requires technical knowledge (prompts, tools, functions) |
| **Architecture** | Single agent per config | No multi-agent orchestration, handoffs, or workflows |
| **Testing** | Basic chat simulator | No automated tests, no red team, no scoring |
| **Deployment** | Direct publish | No versioning, rollback, channel rules, activation logic |
| **Segmentation** | `niche` field (rural/traditional/hybrid/urbano) | Doesn't match new segments (URBAN_REAL_ESTATE, RURAL_REAL_ESTATE, DEVELOPER, BUILDER, LAND_DEVELOPER) |

### Existing Database Tables (Relevant)

- `ai_agents` - Core agent config
- `agent_channels`, `agent_workspaces`, `agent_triggers`, `agent_permissions`, `agent_pipelines`
- `agent_knowledge_sources`, `agent_handoff_rules`, `agent_metrics_config`
- `agent_simulations`, `agent_execution_logs`
- `conversation_memory`, `agent_qualifications`, `agent_learning`
- `organizations` with `niche` field
- `environments` with type (urban/rural)

---

## 2. New Architecture Overview

### Core Concept: AI Workforce Builder

```
User describes operation → Agent Architect designs team → Auto-configures everything → Tests → Deploys
```

### New Segments (Multi-Tenant Isolation)

```
URBAN_REAL_ESTATE     → Imobiliária Urbana (venda, locação, administração)
RURAL_REAL_ESTATE     → Imobiliária Rural (fazendas, sítios, arrendamento)
DEVELOPER             → Incorporadora (empreendimentos, lançamentos, stand)
BUILDER               → Construtora (obras, unidades prontas, financiamento)
LAND_DEVELOPER        → Loteadora (loteamentos, condomínios, tabela dinâmica)
```

   - `niche='rural'` → `RURAL_REAL_ESTATE`
   - Add feature flag for DEVELOPER/BUILDER/LAND_DEVELOPER
4. **Deprecate old tables** after verification

## 4. Backend Architecture

### 4.1 Agent Architect Service

**Location**: `server/services/ai/agentArchitect.js`

**Responsibilities**:
- Receives business context (tenant, segment, business_model, objectives, channels, tools, knowledge, rules)
- Generates complete agent architecture using LLM
- Outputs structured JSON with agents, tools, permissions, guardrails, handoffs, workflows, tests

**Input Schema**:
```typescript

  availableTools: ToolDefinition[];

```

**Output Schema**:
```typescript
interface AgentArchitectOutput {
  operation: {
```

**Prompt Engineering Strategy**:
- Use a powerful model (Gemini 1.5 Pro / GPT-4o / Claude 3.5 Sonnet)
- Structured output with JSON schema validation
- Few-shot examples for each segment
- Chain-of-thought reasoning for architecture decisions

### 4.2 Tool Registry & Policy Engine

**Location**: `server/services/ai/toolRegistry.js`, `server/services/ai/policyEngine.js`

**Tool Registry**:
- Centralized tool definitions with schemas
- Categories: CRM, PROPERTIES, CALENDAR, COMMUNICATION, FINANCING, DOCUMENTS, ANALYTICS
- Each tool: input/output schemas, handler, approval requirements
- Global tools + tenant-specific tools

**Policy Engine** (Critical Security Layer):
```
LLM Tool Request
    ↓
Policy Engine
    ↓
Permission Validation (agent_version.tools ∩ agent_permissions)
    ↓
Schema Validation (input matches tool.input_schema)
    ↓
Rate Limiting / Quota Check
    ↓
Execution (with timeout)
    ↓
Audit Log
    ↓
Return Result or Error
```

**Data Truth Policy Enforcement**:
- Tools MUST return real data
- LLM forbidden from inventing: prices, availability, addresses, metrics, etc.
- System prompt enforces: "NUNCA invente dados operacionais. Use SEMPRE as ferramentas."

### 4.3 Conversation State Manager

**Location**: `server/services/ai/conversationStateManager.js`

**Responsibilities**:
- Maintain structured state per conversation
- Slot tracking (filled/missing/refused/unknown/not_applicable)
- Anti-repetition engine (Question Deduplication)
- Context preservation across handoffs
- Lead memory synchronization

**Anti-Repetition Engine**:
```typescript
interface QuestionDeduplicationEngine {
  // Before asking, check:
  async canAsk(question: string, conversationState: ConversationState): Promise<boolean>
  
  // Detects:
  // - Exact duplicate questions
  // - Semantically equivalent questions  
  // - Data already in slots
  // - Data obtained via tools
  // - Data from CRM/lead_memory
}
```

### 4.4 Conversation Guard Service

**Location**: `server/services/ai/conversationGuard.js`

**Pre-generation checks**:
- Repetition detection
- Required tool usage
- Hallucination risk (confidence thresholds)
- Sensitive data leakage
- Context coherence

**Post-generation checks**:
- Tool calls executed correctly
- Handoff triggers evaluated
- Rule compliance
- Loop detection (same question pattern > 2x)
- Response quality scoring

### 4.5 Loop Detection

**Algorithm**:
- Track last N question-answer pairs
- Detect semantic similarity > threshold
- If loop: block repeat, recover state, generate alternative, log incident

## 7. Technical Decisions & Trade-offs

### 7.1 Agent Architect: Single LLM Call vs. Multi-step

**Decision**: Multi-step with structured output
- Step 1: Analyze business → recommend agent count/types
- Step 2: Design each agent (prompt, tools, config)
- Step 3: Design workflows, handoffs, guardrails
- Step 4: Generate test plan
- **Why**: Better quality, easier debugging, token budget control

### 7.2 Prompt Structure: Structured Blocks vs. Single String

**Decision**: Structured JSON blocks (as specified in requirements)
- Enables: version diff, partial updates, validation, block reuse
- Stored in `ai_agent_versions.prompt` as JSONB

### 7.3 Conversation State: Database vs. Redis

**Decision**: PostgreSQL (Supabase) with JSONB
- Pros: ACID, querying, RLS, no extra infrastructure
- Cons: Latency vs Redis
- **Mitigation**: Cache hot conversations in memory, async write

### 7.4 Anti-Repetition: Prompt-only vs. Engine

**Decision**: Dedicated Engine (Question Deduplication Engine)
- Prompt-only is unreliable
- Engine checks: slots, conversation_state, previous Q/A, tool results, CRM data
- Runs as pre-generation guard

### 7.5 Multi-Agent Handoff: Context Passing

**Decision**: Full state transfer with summary
- Protocol: `{ from_agent, to_agent, reason, conversation_id, lead_id, state, summary }`
- Preserves: slots, context, lead_memory, intent, history
- Target agent receives condensed summary + full state access

### 7.6 Tool Execution: Direct vs. Policy Engine

**Decision**: Policy Engine (mandatory)
- Security: Least privilege, audit, validation
- Allows: rate limiting, approval workflows, schema enforcement
- **No direct LLM → DB access ever**

## 8. Security Considerations

| Area | Implementation |
|------|----------------|
| **Multi-tenancy** | All tables have `organization_id`, RLS policies |
| **Data Isolation** | No cross-tenant queries, knowledge, agents, conversations |
| **Prompt Injection** | Separation of contexts (SYSTEM/TENANT/AGENT/USER), input sanitization |
| **Tool Access** | Policy Engine enforces least privilege per agent version |
| **Secrets** | API keys only in server env, never in frontend |
| **Audit Trail** | Every config change, publish, rollback, handoff logged |
| **PII in Logs** | Redact phone, email, CPF, document numbers in execution logs |

## 10. Risk Assessment & Mitigation

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| Agent Architect hallucinates bad architecture | Medium | High | Structured output, validation, human review step |
| Tool Policy Engine becomes bottleneck | Low | High | Async execution, caching, connection pooling |
| Conversation state grows too large | Medium | Medium | TTL cleanup, archival, slot-only storage |
| Prompt injection bypasses guards | Low | Critical | Multi-layer: separation, sanitization, red team |
| Multi-agent handoff loses context | Medium | High | Comprehensive state transfer protocol, testing |
| AI Red Team false positives | Medium | Medium | Human review queue, severity classification |
| Cost explosion from LLM calls | Medium | High | Model routing, token budgets, caching, monitoring |
| Migration breaks existing agents | Medium | High | Parallel run, feature flag, gradual rollout |
